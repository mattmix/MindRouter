Detection Action

For each severity, choose what happens when DLP detects sensitive data: Block the request (the caller receives a 422 with a clear explanation), Redact the offending text (e.g. an SSN is replaced with [REDACTED] before the model or the user sees it), and/or Alert by email. All three are independent — enable any combination. Alerting is asynchronous and adds no latency; Block and Redact run an inline scan and only add latency when at least one is on. Block takes precedence over Redact (a rejected request has nothing to redact).

What the inline Block and Redact actions inspect. Prompt only (default) acts before generation and does not affect streaming. On the response side, block/redact apply to non-streaming replies (a streamed reply is already on the wire, so it is alert-only). Redaction keeps the original in the audit log and alert — only the text sent onward is masked. If the scanners are unavailable, inline actions fail open — the request proceeds and the gap is logged — so a DLP outage cannot take down the gateway. The inline scan uses regex + GLiNER on the off-host pool.

Web Search Screening Help
What it does

Before any search query is sent to a provider (Brave, SearXNG, …), it is scanned with your current DLP configuration. The sequence is:

  1. Scan the query with the enabled scanners and your severity rules.
  2. If the worst finding reaches Act at severity, redact every non-ignored finding — an SSN becomes [REDACTED: social security number].
  3. Re-scan the redacted query. Redaction is value substitution, so an overlapping or normalized match can survive it; this pass is what proves the query is actually clean.
  4. If it still reaches the bar, the search is blocked. Nothing is sent, and the caller gets a clear message instead of results.
Which searches are covered

All of them — the /v1/search API, the Responses API web_search tool, the MCP search tool, dashboard chat auto-search, the admin test query, and catalog enrichment. They share one code path, so none can bypass screening.

Audit trail

Each screened search records the query submitted by the caller, the query actually sent, and a pass-by-pass table — every DLP pass with the exact text it scanned and whether it passed or failed. A blocked search records how far masking got and that nothing was sent. Redaction masks the whole flagged span with asterisks, so ssn 456-78-9012 becomes *** ***********; masking a value often exposes the label word beside it, which is why a second round is common.

What is recorded

Every screened search gets a row in Audit Log → Web search with the outcome (none, redacted or blocked), the severities from both passes, the categories, and masked evidence snippets. A redacted search stores the redacted query, so the audit log never becomes a second copy of the data screening just refused to send.

Screening does not raise its own DLP alert emails: the same text is already covered by the normal post-request scan, and double-alerting one event helps nobody.

Blocked searches your users will notice

A category the scanner flags as a phrase rather than a value (GLiNER reporting the words “Social Security numbers” in a policy question, for example) cannot be usefully redacted, so such a query blocks. If that is noise for your traffic, set that category to Ignore in Severity Rules and it is excluded from screening as well.

Regex & Keyword Scanner Help
How it works

The regex scanner is the fastest tier (~0.1ms). It runs every rule in the Patterns & Keywords list against the full text of each request and response. The list ships pre-filled with the built-in patterns; they are ordinary lines you can edit or delete, and Restore built-ins re-adds any that are missing.

Saving

Every line is validated when you save: a regex that does not compile, a pattern line with a missing field, or a one-character keyword is rejected with the line number and nothing is written.

Max scan characters

The scan text is every message, the prompt, and the model's reply concatenated in order, so on a long conversation the newest turns are at the end. With a limit set, anything past it is silently not scanned (a dlp_scan_text_truncated line is logged). No limit (stored as 0) removes that ceiling entirely so DLP cannot be circumvented by padding a prompt. A positive limit must be at least 1000.

GLiNER NER Scanner Help
How it works

GLiNER is a neural named entity recognition (NER) model that detects sensitive entities in natural language text. Unlike regex, it understands context — it can detect names, phone numbers, and IDs even when they don't match a fixed pattern.

The model (urchade/gliner_multi_pii-v1, ~200MB) loads lazily on the first scan (~2-3 seconds). Subsequent scans take approximately 10ms on CPU.

Confidence threshold

The slider controls the minimum confidence score (0.0–1.0) for a detection to be reported. Lower values catch more entities but may produce false positives. Recommended: 0.5 for balanced detection, 0.7 for high precision.

Entity categories

Check the categories you want GLiNER to scan for. The built-in categories cover common PII types. You can also add custom categories by typing a name in the text field and clicking Add.

Custom categories work because GLiNER is a zero-shot model — it can detect entity types it wasn't explicitly trained on, as long as the category name is descriptive. Good custom categories:

  • vandal id — University of Idaho student IDs
  • grant number — Federal grant identifiers
  • diagnosis — Medical diagnoses (HIPAA)
  • grade — Student grades (FERPA)
  • medication — Drug/prescription names (HIPAA)
Dependencies

Requires the gliner Python package. The Docker image installs it automatically from pyproject.toml.

LLM Contextual Scanner Help
How it works

The LLM scanner sends the text to a dedicated language model for semantic analysis. Unlike regex or NER, the LLM understands context — it can detect that "my student John got a B+ in CS101" is a FERPA violation even though no single word is PII on its own.

The scanner dispatches directly to a healthy backend serving the model you name, chosen from the live registry. No API key is involved, scans never re-enter the gateway, and they create no request records — so a scan cannot re-store the content it just flagged, cannot consume a user's quota, and cannot trigger a scan of itself.

Model selection

Enter any model name available in MindRouter. A small, fast model is ideal since DLP scans run in the background. Recommended: qwen/qwen3.5-4b or similar ~4B parameter model.

System prompt

The system prompt instructs the LLM what to look for and how to format its response. The default prompt asks for a JSON array of findings. You can customize it to focus on specific compliance regimes:

  • FERPA focus — Add: "Pay special attention to student records, grades, enrollment status, financial aid, and disciplinary records."
  • HIPAA focus — Add: "Focus on protected health information including diagnoses, treatments, medications, lab results, and patient identifiers."
  • CUI focus — Add: "Look for controlled unclassified information including export-controlled data, law enforcement sensitive data, and ITAR/EAR restricted content."
Performance

Typical latency is ~500ms depending on the model and text length. Text is truncated to 8,000 characters to limit token usage. The scan runs asynchronously after the response is delivered — it never delays user requests.

Severity Rules Help
How severity works

When DLP detects sensitive data, each finding has a category (e.g. "social security number", "email"). The severity rules map each category to a severity level. The highest severity among all findings in a single scan determines the alert level.

Severity levels
LevelMeaningTypical categories
MajorImmediate attention required. High-risk data exposure.SSN, credit card, bank account, passport, medical record
ModerateReview recommended. Potential compliance issue.Driver license, date of birth, student ID, vandal ID
MinorInformational. Low-risk but worth logging.Person name, email address, phone number
IgnoreDropped entirely. Findings in this category are discarded before anything downstream sees them: no alert row, no email, no block or redact, and no trace in the DLP log. GLiNER is not even asked for an ignored category.A category that only produces noise in your traffic
Adding rules

Type the category name (must match exactly what the scanner reports) and select a severity level. Categories from the GLiNER scanner match the checkbox labels in lowercase (e.g. "person", "social security number"). Custom regex pattern categories match the category field you defined.

If a detected category has no rule, it defaults to Moderate. A scan whose only findings are in ignored categories is treated as clean.
